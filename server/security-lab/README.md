# Локальный стенд проверки egress (не production gateway)

Docker Desktop с Linux Engine: `docker compose -f server/security-lab/compose.yaml up -d --build egress registry`.
Scanner запускается по требованию: `docker compose -f server/security-lab/compose.yaml run -T --rm scanner --version`.
Остановка: `docker compose -f server/security-lab/compose.yaml down`.
Проверка правил и реального Trivy в Docker: `python3 -m unittest discover -s server/security-lab -p 'test_*.py'`. Интеграционные проверки требуют Docker и могут тянуть образ scanner из сети; отключённый Docker пропускает интеграционные тесты, поэтому проверяйте число skipped. Не запускайте проверки с реальными registry credentials.

`scanner` находится только в Docker internal network; `egress` подключён к ней и к внешней сети. Ни одному контейнеру стенда не передан Docker socket, а scanner не подключён к внешней сети. Локальный proxy принимает только CONNECT на порт 443 для явно перечисленных хостов, при каждом соединении проверяет DNS-адрес и подключается именно к проверенному публичному IP. Настройки proxy нельзя считать утверждённой политикой registry: разрешённые хосты в `compose.yaml` — примеры для лаборатории. Не помещайте credentials в compose или логи.

**Ограничения:** стенд проверяет сетевой каркас и политику CONNECT, но не интегрирован с NestJS/API, SQLite ledger, registry resolver или реальным заданием Trivy; DB scanner ещё не подготовлена. Не считать HTTP 202 или P0 scan реализованным. Тесты `test_integration.py` проверяют реальный Trivy 0.69.3: отсутствие socket, невозможность прямого доступа без proxy, отказ чужому registry и отказ blob redirect Docker Hub на `production.cloudfront.docker.com`. Unit-тесты запрещают смешанные DNS-ответы и повторное разрешение в приватный IP. Дополнительно `registry.py`/`Dockerfile.registry` поднимают одноразовый HTTPS OCI registry с самоподписанным сертификатом и фиксированным fixture digest. Реальный Trivy с `--insecure` (только для тестового сертификата) успешно читает его manifest/blob; тесты проверяют отказ на manifest/blob redirects к metadata, Bearer token realm к metadata/чужому host, повторный CONNECT при моделируемом rebinding и невозможность прямого scanner доступа. Адрес 172.30.91.10 разрешён proxy **исключительно** для точного имени `registry.lab.test` при `LAB_FIXTURE=1`; это лабораторное исключение не переносить в production. Режимы ответа fixture переключаются в `/tmp/mode`, сетевой тест rebind подменяет ответ DNS на metadata в `/tmp/rebind` между отдельными реальными вызовами Trivy (не полноценная атака на системный DNS). Дополнительный тест удаляет tag и подтверждает успешный реальный scan по полученному от fixture digest с `--platform linux/amd64`; это только проверка возможности Trivy работать с закреплённой целью, а не реализация resolver/ledger, транзакционной фиксации платформы и идентификатора задания. Тест не доказывает идемпотентность, production TLS или полную безопасность Trivy. Production cloudfront не в allowlist, поэтому настоящий scan Alpine завершается отказом, а не успешным отчётом. Не добавлять CDN в allowlist без пересмотра угроз и защищённых тестов. Trivy при ошибке может включить подписанный URL blob redirect в stderr: `diagnostics.py` выдаёт только код и exit status, тестовый runner немедленно сводит raw stderr к булевым признакам; не передавать raw logs в API, не публиковать stderr в CI. В будущей worker-интеграции использовать такую же политику на границе процесса (включая Docker/compose ошибки). До безопасного устранения этого риска, реализации API/ledger и полной приёмки нельзя возвращать HTTP 202. CONNECT-туннель не анализирует зашифрованный HTTP-трафик: безопасность зависит от изоляции scanner, набора разрешённых хостов и проверки TLS клиентом; для production нужны отдельная оценка и усиление.
