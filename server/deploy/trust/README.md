# Локальная аттестация Trivy vulnerability DB

Это **подпись локального оператора**, НЕ подпись Aqua Security. Публичный Ed25519-ключ `db-signing-key.pub.pem` закреплён в репозитории; SHA-256 его DER/SPKI: `d75c6f6b2384de68978090fc837387ab4f3e878ee004bccf27ea98a84fbee078`. Закрытый ключ локального стенда — `.local-auth/trust/db-signing-key.pem` (0600, игнорируется Git). Перенесите резервную копию ключа в защищённое хранилище оператора; потеря ключа означает ротацию публичного ключа по отдельному ревью, утечка — отзыв и перевыпуск DB release. **Не** передавать закрытый ключ контейнерам, worker, скачивающему процессу, CI или Git.

Существующий локальный ключ создан на этой же машине *после* первоначальной HTTPS-загрузки DB. Подпись фиксирует именно принятое нами содержимое, но не является независимым доказательством издателя/истории первой загрузки. Издательская подпись не заявляется.

## Operator usability v2 (DIP-TASK-40)

Для **новых** серверных CVE admissions используется `cve-db-updated-at-14d-v2`: настоящий signed `UpdatedAt` не старше **14 суток включительно**, точное сравнение UTC integer-nanoseconds без округления/age grace. `DownloadedAt` не омолаживает данные. `NextUpdate` — publication hint, не отдельный срок operator expiry: его достижение даёт `DB_PUBLICATION_OVERDUE`, возраст данных >24h — `DB_DATA_OLDER_THAN_24H`. Warnings не снимают signature/key/source/schema/hash/file/mount/readiness gates. Invalid calendar, future >300s, download-before-update и неверный publication interval по-прежнему fail-closed. Исторический signed descriptor остаётся **envelope v1**; менять bytes/dates или переподписывать прежний release ради «свежести» запрещено.

Единый evaluator — `server/api/src/worker/cve-db-policy.mjs`; Python proof делегирует ему через public metadata-only CLI, не через `datetime`. CLI metadata не аутентифицирует release. `verify-vuln-db-release.ts` аутентифицирует public-key signature и закреплённые bytes, затем выводит фактические даты/receipt/derived `usableUntil`; это **не** scanner/HTTP/combined acceptance proof. Admission и worker сохраняют отдельный marker; migration14 привязывает уже существующие CVE scans к frozen `legacy-db-freshness-v1`, не меняя history/replay. Ledger финализирует receipt одним clock capture внутри current-attempt fence; worker `checkedAt` не заменяется commit-time. History валидируется по исходным временам, не по today.

При discovery outage refresh отдельно проверяет unchanged active release и readiness, показывает warnings, **сохраняет nonzero update error** и не скачивает/подписывает/меняет pins в fallback. Unchanged tag также не означает newest DB или успешную новую публикацию. Проверять этот operator flow может только parent: автор TASK40 не выполняет signer, Docker/Compose, private env/key read, LIVE или rollout. Новый isolated LOCAL combined positive на unchanged authentic DB ещё требуется; существующий `test_nginx_local_path.py` читает private stand env и проверяет LIVE health, поэтому без отдельной parent authority не является безопасным авторским workflow.

## Автоматический локальный стенд (осознанно ослабленная модель доверия)

По явному разрешению владельца локальный операторский `refresh-local-stand.py` может без ручного утверждения каждого выпуска обнаружить `:2`, скачать **по exact manifest digest** через проверенный HTTPS, проверить слой и DB, отдельно подписать локальным ключом, выполнить offline OS+Node proof и переключить только `api`/`worker` на новый read-only release. **Подпись при этом НЕ удостоверяет Aqua Security:** владелец сознательно доверяет HTTPS/GHCR и собственной проверке хешей вместо подписи издателя. Процесс запускается только на операторском хосте; его нельзя переносить в worker, CI или downloader. Закрытый ключ остаётся 0600 на хосте. При ошибке перед переключением предыдущий выпуск остаётся активным; при неуспешном пересоздании или container preflight возвращаются старые pin и пересоздаются старые контейнеры. Crash/потеря питания и неуспешный rollback требуют проверки оператором: автоматического доказательства E2E через браузер нет. Истёкший DB запрещает CVE-проверки (не превращается в «0»).

Прямой запуск из корня репозитория: `python3 server/deploy/trust/refresh-local-stand.py`. Для локального macOS launchd приватный `.local-auth/db-refresh.plist` (в этом стенде скопирован в `~/Library/LaunchAgents/io.diplom.trivy-db-refresh.plist` для запуска после входа) задаёт период 21600 секунд и рабочий каталог репозитория; если меняется Node/Python/Docker path или путь репозитория, обновить plist и перезапустить агент. Проверить состояние `launchctl print gui/$(id -u)/io.diplom.trivy-db-refresh`, остановить `launchctl bootout gui/$(id -u)/io.diplom.trivy-db-refresh`. Период запуска считается от загрузки задания, это не гарантия обновления до `NextUpdate`: отслеживайте отказы в `.local-auth/db-refresh.log` и свежесть active DB. Автоматических уведомлений об отказе нет; неизвестный exit code/лог — повод проверить стенд вручную. Если появился `.local-auth/.trivy-refresh.lock` или незавершённый каталог release, **не удаляйте их без расследования**: автоматический retry fail-closed. Сохраняйте предыдущий выпуск до ручной проверки полноценного HTTP CVE E2E.

## Выбор exact LOCAL-композиции (Stage 1)

По умолчанию и при отсутствующем `.local-auth/stand-composition.json` используются только **оба** базовых файла; nginx закрыт в default API и worker. Новый LOCAL — отдельные compiled entrypoints `nginx-local.main.ts` / `nginx-local-worker.main.ts`, выбранные фиксированным третьим `server/deploy/compose.stand.nginx.local.yaml`. Это не permission/JWT override и не env-флаг произвольных registry/tags/checks. Обычные account/cookie/Origin/owner guards, production public anchor, signed fresh RO DB и `1 GiB`/swap `0` остаются обязательными.

**Автор не активировал LIVE.** Интегратор включает LOCAL только после трёх новых ревью diff, SQLite online backup и проверки composition. Базовый допустимый NONSECRET descriptor: `{"profile":"nginx-local","overlay":"server/deploy/compose.stand.nginx.local.yaml"}`; обратный выбор — `{"profile":"default"}`. Использовать общий `stand_composition.refresh_lock()` и `write_descriptor_locked(repo, profile, capability)` с capability, полученным из этого же действующего lock-контекста; ручная запись поверх чужого lock запрещена. Selector отвергает неизвестные/дублированные поля, другой path/profile, links, unsafe permissions и не принимает CLI/env override пути overlay. Helper возвращает прежние bytes для операторского rollback; он сам не подписывает, не меняет DB pins/JWT и не запускает Docker. TASK37 добавляет только фиксированный opt-in `llm: "openrouter-free"` к **nginx-local** descriptor; это выбирает четвёртый `compose.stand.openrouter.free.yaml`, не произвольный overlay. `write_descriptor_locked(..., llm='openrouter-free')` включает, `llm=None` выключает; без аргумента сохраняется текущий выбор, не сбрасывается незаметно. Selector проверяет лишь metadata private API `server/.env.local` (owner, regular/no symlink, 0600, <=8192 bytes), не читает значение. Refresh фиксирует и четвёртый overlay через switch/verify/rollback. Parent-only команда после reviews/backups/approved privacy: `python3 server/deploy/trust/deploy-openrouter-free.py --deploy-after-review`; подробности и ограничения — `server/deploy/proof/openrouter-free.md`.

Для config/up/recreate/verification/rollback интегратор использует один frozen `select(repo).command` под тем же lock. Timer вызывает `refresh-local-stand.py`, который читает descriptor **один раз под lock** и сохраняет этот выбор до конца обновления и rollback. Поэтому refresh не заменяет LOCAL на default entrypoints. LOCAL readiness требует `chainReady()` **и** свежий versioned `/data/nginx-local.ready`; один healthy API недостаточен. Не копировать закрытый ключ в descriptor, API/worker/container/CI; ключ остаётся только у существующего host publisher.

При rollback сначала вернуть прежние DB pins, пересоздать выбранную композицию, проверить signed DB и readiness; отдельный rollback профиля выполняется под общим lock с descriptor `default` и обоими базовыми файлами. При crash/stale lock или неуспешном rollback — остановить unattended действия, проверить env/descriptor/контейнеры вручную, не удалять lock автоматически. JWT, auth/ledger volumes и исторические scan rows не сбрасывать. Fresh isolated acceptance воспроизводится `python3 -m unittest server.deploy.proof.test_nginx_local_path`: собственные volumes и обычные заранее зарегистрированные аккаунты, HTTP+Chromium+SQLite/recreation, без LIVE активации, raw logs или signing key access. Это не повтор ARTF28 expiry matrix и не полная приемка TASK2.

## Ручной выпуск (отдельно от downloader и сети worker)

1. Оператор отдельно проверяет официальный источник `ghcr.io/aquasecurity/trivy-db`, фиксирует OCI manifest digest, digest слоя, SHA-256 локального `bundle.bin` и `db/trivy.db` в своей записи о выпуске. `:2` — изменяемый указатель **только для обнаружения** обновления. Ограниченный downloader работает **вне** `scan_internal` по HTTPS с обычной проверкой TLS, точным OCI digest и allowlist blob CDN; ключ подписи ему недоступен. Он не добавляет никаких hosts в egress worker и не включает новый выпуск автоматически:

   ```sh
   node server/deploy/trust/fetch-db-layer.mjs discover
   node server/deploy/trust/fetch-db-layer.mjs stage-latest /absolute/.local-auth/trivy-db-candidates
   # После независимой проверки manifest и layer digest из кандидата:
   python3 server/deploy/trust/prepare-db-release.py /absolute/candidate /absolute/new-release sha256:<reviewed-manifest> sha256:<reviewed-layer>
   ```

   `stage-latest` можно вызывать планировщиком каждые 6 часов (например, `0 */6 * * *`, с абсолютными путями к Node, скрипту и приватной директории кандидатов): он только готовит **неподписанного** кандидата. Планировщик на этой машине не установлен — команда доступна для явной настройки оператором; не добавляйте signing key в его окружение. Конвертер отвергает посторонние tar members, пути, links и превышение лимитов, записывает DB и gzip ровно этой DB (OCI слой сам является *gzip от tar*, а не локальным `bundle.bin`) и выставляет реальное `DownloadedAt`. Новый выпуск — отдельный каталог только с `bundle.bin`, `db/trivy.db`, `db/metadata.json`; изменять подписанный выпуск запрещено. Автоматически доверять новому содержимому `:2` или подписывать его ключом downloader нельзя: наша подпись не подтверждает Aqua Security.
2. На машине оператора выполнить (параметры берутся **из проверенной записи**, не из descriptor):

   ```sh
   node server/deploy/trust/sign-offline-db.mjs /absolute/release-directory .local-auth/trust/db-signing-key.pem server/deploy/trust/db-signing-key.pub.pem sha256:<reviewed-oci-manifest> <reviewed-bundle-sha256> <reviewed-db-sha256>
   ```

   Подписант требует закрытый ключ 0600, сверяет его с закреплённым открытым, hash сжатого и распакованного файлов и что gzip распаковывается точно в эту DB, проверяет schema 2 и сроки `UpdatedAt`/`DownloadedAt`/`NextUpdate`, подписывает канонический `descriptor.json` в `descriptor.sig`. Повторная подпись в том же каталоге запрещена. Ключ не используется downloader'ом.
3. Перед каждым использованием проверить **закреплённым ключом** и independently pinned hash:

   ```sh
   pnpm --filter @diplom/scan-api exec tsx src/worker/verify-vuln-db-release.ts /absolute/release-directory sha256:<reviewed-oci-manifest> <reviewed-bundle-sha256>
   ```

   При фактическом возрасте `UpdatedAt` >14 суток, invalid timestamps, подмене DB/metadata или чужой подписи — отказ, а не «0 CVE». Старые `DownloadedAt` и publication `NextUpdate` сами по себе не блокируют v2. Возврат verifier `authenticated-release-usability-only` **не является** доказательством пригодности DB для сканера или combined HTTP admission: отдельно нужен допустимый isolated workflow с настоящим уже-qualified immutable worker и теми же pins.

Подпись в рабочем каталоге сериализуется `.signing.lock`, но пара `descriptor.json`/`descriptor.sig` не публикуется атомарно: crash оставит неполный выпуск и lock до ручной проверки. Не удаляйте lock без расследования; полная атомарная публикация read-only каталога — следующий этап. Проверка сама по себе не замораживает файлы после хеширования: в будущей цепочке потребитель обязан проверять неизменяемый снимок при использовании.

Локальный стенд включает CVE **только** с дополнительным `server/deploy/compose.stand.vuln.local.yaml` поверх `compose.stand.yaml` и сохранённым `.local-auth/stand.env` (не запускать `stand:auth` поверх существующих томов: сменится JWT secret):

```sh
docker compose --env-file .local-auth/stand.env -f server/deploy/compose.stand.yaml -f server/deploy/compose.stand.vuln.local.yaml up -d --build api worker web
```

Опциональный override берёт три **операторских** pin из игнорируемого `.local-auth/stand.env`: `SCAN_VULN_RELEASE_HOST_DIR` (абсолютный путь к новому проверенному release), `SCAN_VULN_MANIFEST_DIGEST` и `SCAN_VULN_ARTIFACT_SHA256`. Существующий `SCAN_JWT_SECRET` в этом файле **сохранять**: пересоздание через `stand:auth` поверх volumes сбрасывает авторизованные сессии. После подписи и проверок сделать каталог/подкаталоги доступными на чтение и исполнение UID 65532 (`chmod 0555`), файлы — только на чтение (`chmod 0444`); закрытый ключ остаётся 0600 ВНЕ release. Заменить три pin в private env одним шагом, проверить `docker compose ... config --quiet` и пересоздать только `api worker` с обоими Compose-файлами, затем повторить authenticated CVE E2E. Не изменять release, на который ещё ссылаются контейнеры; предыдущий хранить до доказанной успешной ротации.

Историческая запись выпуска (не проверка текущих active pins): OCI `sha256:23b403a78807d762f6ecf1b85f526c1681a075020549ad78e4a604f84a87e02b`, `NextUpdate=2026-10-05T08:52:32Z`. API перед постановкой задания, а worker перед CVE-этапом заново проверяют закреплённый ключ, подпись, хеши и сроки; DB и release read-only, scratch — отдельный tmpfs UID 65532. Новые CVE admissions отказывают после фактических 14 суток данных, а не только из-за publication NextUpdate; старые jobs/history сохраняют исходную legacy policy. Отказ не означает «0 CVE». Автоматическая подпись и переключение возможны **только** в явно разрешённом локальном режиме выше; гарантий бесперебойного обновления и подлинности издателя НЕТ; файл на машине хоста может быть изменён привилегированным процессом даже при read-only bind. Без независимой подписи издателя нельзя выдавать unattended TLS download + подпись нашим же ключом за проверку provenance.

Подтверждённый локальный E2E: отдельный CVE и совмещённый Secrets+SBOM+CVE на pinned `library/alpine`/`linux/amd64`; современный Alpine с 16 APK дал 0 CVE, старый pinned Alpine 3.16 дал 4 CVE и после замены DB — тоже 4. Это **только** находки в конкретном образе и сроке DB, не размер общей базы и не гарантия безопасности. Синтетический офлайн fixture даёт OS и Node CVE, но ещё не подтверждает полный позитивный HTTP-путь для Node/OS уязвимого remote image. Работающий контейнер и ОС хоста не поддерживаются этим worker: нельзя принимать `scope=host` или использовать Docker socket/host filesystem mount в worker. Для них требуются отдельные авторизация, snapshot/provenance и границы доступа (см. `DIP-TASK-5`, `DIP-TASK-8`). TLS + собственная подпись защищают локальную цепочку после решения оператора, но не удостоверяют автора исходного OCI-артефакта.
