# Deployment

## Frontend + auth + restricted live Alpine/secret stand

`compose.stand.yaml` builds React/nginx, auth API, persistent auth SQLite, separate persistent scan ledger, isolated worker and registry egress gateway. nginx routes **only** `/api/v1/auth/*`, `/api/v1/browser/scans`, child GET routes and the exact UUID-shaped child `POST /api/v1/browser/scans/:scanId/cancel` to the API. The original JWT-only `/api/v1/scans` and all other `/api/*` URLs return 404; the API and worker publish no ports. Only web publishes `127.0.0.1:8080`. The browser API requires a current HttpOnly session and, by default, explicit `SCAN_BROWSER_ALLOWED_USER_IDS` enrollment; unset/empty denies all. The local-only opt-in `SCAN_BROWSER_ALLOW_ALL_LOCAL_ACCOUNTS=true` admits all authenticated accounts (including newly registered ones) **only** when `AUTH_ORIGIN=http://127.0.0.1:8080` and `AUTH_ALLOW_INSECURE_LOCAL_HTTP=true`. It does not grant access to guests, relax scan target/rate limits or expose the JWT API; at any other origin requesting the override disables browser scan access instead of falling back to the allowlist. It uses the account ID as ledger subject, checks Origin on POST, and never exposes the JWT secret. Only Alpine image/secret checks are supported. `.dockerignore` excludes local env files, databases and Git from image build contexts.

For a **temporary, trusted local demo**, `pnpm stand:auth` opts in to all authenticated accounts by default. Register at `http://127.0.0.1:8080/register`, then open `/scans/new`; guest requests remain denied. Any person able to register on this local stand can now start a bounded Alpine/secret scan: do not forward port 8080, proxy it to the internet, or use the demo override with public deployments. To restore explicit per-account access locally, run `SCAN_BROWSER_ALLOW_ALL_LOCAL_ACCOUNTS=false SCAN_BROWSER_ALLOWED_USER_IDS=<32-character account id> pnpm stand:auth`; to disable scans, set the override false and leave the allowlist empty. Enrollment by email is forbidden because an unverified address could be registered by somebody else first. The shortcut sets an ephemeral JWT secret and allows loopback HTTP only for local testing. The backend still enforces bounded attempts and the checked Alpine/secret target; `POST` will return 503 when worker/gateway is unavailable. The `auth_accounts` and `scan_ledger` volumes survive restarts; do not use `docker compose down --volumes` if they matter. The login limit is keyed on the nginx socket IP, so repeated local logins can temporarily throttle the stand; this must be fixed at the trusted edge before a public deployment.

To expose this stack behind an existing HTTPS reverse proxy **on the Docker host**:

1. Provision a DNS name and trusted TLS certificate; point the host's TLS reverse proxy at `127.0.0.1:8080` (for example, a Caddy virtual host with `reverse_proxy 127.0.0.1:8080`). The public URL must be HTTPS. Do not expose port 8080 directly to the internet; check the host firewall too.
2. Supply `AUTH_ORIGIN` as the **exact** browser origin, e.g. `https://stand.example.org` (no trailing slash), and `SCAN_JWT_SECRET` as a unique random secret of at least 32 bytes in a protected environment file **outside this repository** (e.g. `/etc/dip/stand.env`, mode 0600). Set `AUTH_ALLOW_INSECURE_LOCAL_HTTP=false`, and supply `SCAN_BROWSER_ALLOWED_USER_IDS` as an explicit comma-separated operator-managed list of **already created account IDs** (never an open wildcard or unverified email). Never use a sample/domain/secret literally; do not add the environment file to the image, frontend, Git, or logs.
3. On the Docker host run `docker compose --env-file /etc/dip/stand.env -f server/deploy/compose.stand.yaml up -d --build`. Check `docker compose --env-file /etc/dip/stand.env -f server/deploy/compose.stand.yaml ps` and `https://<your-domain>/api/v1/auth/me` (401 when anonymous); register via the **same** HTTPS origin. Back up `auth_accounts` and `scan_ledger` separately, including each SQLite WAL consistently (SQLite backup API or offline copy); set retention, monitoring and restore procedures.

**Limits:** deployment is not complete until the actual domain, host, TLS, firewall, backup and external abuse/rate controls are supplied and checked. Current per-IP auth throttling sees the proxy's socket IP, not a validated real client IP, and can throttle unrelated visitors sharing the proxy; plan and validate per-client limiting at the trusted edge before inviting public traffic. Outside the explicit local demo override registration alone does not authorize a scan: only explicitly enrolled accounts can use the narrow browser API. JWT-only `/api/v1/scans` stays private; browser cancel is limited to an enrolled session and queued/running scans owned by that account (an accepted cancel is terminal in the ledger, but process termination is best effort). The local stand has bounded SSE with heartbeat and exclusive replay; the UI uses SSE as a hint and confirms changes with GET, falling back to polling. SSE limits are per API process, not distributed across replicas. CVE/SBOM and public exposure are **not** accepted. Do not expose the stand until the external abuse controls and independent security review are completed.

## Protected Alpine/secret slice — pending independent acceptance

`compose.yaml` keeps the API and worker exclusively on `scan_internal`; no API port is published, no Docker socket or direct external route is mounted. The gateway is the only dual-homed process. TLS verification and the exact three-host allowlist remain enabled; lab fixtures and insecure TLS are not production configuration.

`scan-readiness.ts` refuses new jobs with 503 when worker heartbeat, gateway or isolated network connectivity are unavailable. Operational heartbeat and TCP checks alone do not prove the complete production boundary; deployment must use the verified Compose topology. An already committed job can still be replayed by subject/key before readiness. Do not replace runtime checks with an environment-only flag or publish an ingress without separate review.

Validation:

- `pnpm --filter @diplom/scan-api test`, `pnpm --filter @diplom/scan-api typecheck` and migration/backup/restart tests.
- `python3 -m unittest discover -s server/deploy -p 'test_*.py' -v` checks the public-policy gateway, actual API/worker direct-connect and daemon denial, TLS, Trivy NO_PROXY denial, positive 202→terminal and outage-replay; require zero skips and zero expected failures.
- `python3 -m unittest server/deploy/proof/test_production_path.py -v` uses disposable trusted-CA OCI fixtures with the same gateway handler and actual API/worker/Trivy. It verifies same-tag mutation, forbidden redirects, mixed DNS and rebinding with upstream-hit counters. The test-only exact fixture-IP policy and CA must never be deployed with the public gateway.
- `python3 -m unittest discover -s server/security-lab -p 'test_*.py' -v` checks the separate lab fixture. Its self-signed CA, private test DNS and `--insecure` cannot stand in for the production policy.

The controlled proof suite and public-policy Docker smoke must both pass before three fresh independent spec/correctness/security reviews and task-level acceptance. No public ingress is currently configured; adding one requires separate review. Full CVE/SBOM and public release are outside this Alpine/secret slice. Cookie-bound cancellation and bounded live SSE are implemented for the local stand; neither constitutes acceptance of the full P0 audit or public exposure.
