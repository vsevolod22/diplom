# Scan API — fail-closed scaffold

`pnpm --filter @diplom/scan-api test` and `pnpm --filter @diplom/scan-api typecheck` (Node 23.11 was used for validation).

`src/app.module.ts` imports `ScansModule`, which composes `SecurityModule`, `OciModule`, `AuthModule` and `LedgerModule`; `src/main.ts` is only the HTTP bootstrap. The worker runs as a separate isolated Compose service in the assembled local stand. NestJS constructor dependencies use explicit `@Inject` tokens so the tsx runtime resolves providers consistently.

`src/ledger/ledger.ts` uses Drizzle ORM with `better-sqlite3` and persists immutable pinned targets and an outbox in one `BEGIN IMMEDIATE` transaction. The versioned migration preserves existing v1/v2 rows; `claim` uses expiring leases/attempts, `finish` rejects stale acknowledgements, `retry` schedules another attempt, and `prune` removes terminal rows after 30 days. Tests exercise migration, rollback, backup/restore with WAL, concurrent connections, restart, stale ack and replay. The separate worker loop consumes persisted outbox jobs. See `src/ledger/README.md` before deployment. Pin and validate a supported Node LTS and native addon build on a clean CI install; use one persistent SQLite volume, never an ephemeral container filesystem.

The POST route enqueues and returns 202 only after isolated-chain readiness and a pinned target; otherwise it fails closed. Startup requires a dedicated `SCAN_JWT_SECRET` (at least 32 bytes), `SCAN_JWT_ISSUER`, `SCAN_JWT_AUDIENCE`; signed HS256 JWT must carry `sub`, `iat`, short `exp` and `scan:create` scope. Never reuse a single API token as user identity; protect these secrets outside the repository. Unauthorized requests return 401, authorized requests 503. The API is reachable only on internal Compose networks; the local web proxy forwards only cookie-bound `/api/v1/browser/scans` and auth, never the internal JWT endpoint. `src/scans/image-reference.ts` rejects ambiguous/untrusted names. `src/oci/registry-resolver.ts` verifies pinned digest/platform through the isolated CONNECT gateway with a narrow Docker Hub token/redirect policy. `src/worker/scan-worker.ts` constructs a digest-only Trivy command with remote source, no inherited Docker env and sanitized failure codes; network isolation is enforced by the verified deployment topology, not by this module alone. No raw scanner findings or stderr should be persisted or exposed.

Before accepting a deployment as production-ready: deploy and verify an independently enforced production gateway and scanner network isolation (NOT the lab `LAB_FIXTURE`/self-signed TLS/`--insecure`), complete manifest config/blob/platform validation and trusted token flow, integrate authenticated request parsing/replay → resolver → SQLite → worker with readiness checks and response handling, verify safe DB availability and normalized findings, and run end-to-end positive/negative tests. The TLS registry in `../security-lab/` is a lab fixture **not** a production gateway.

## Docker Hub discovery limits (not scan admission)

Cookie-authenticated `GET /api/v1/browser/scans/images?q=...&generation=...&cursor=...` returns `{items,nextCursor,state,loaded,pages,policy}`. Queries are 2–64 characters; the caller starts a fresh generation without a cursor and explicitly requests subsequent pages. Only fixed HTTPS Hub endpoints are requested through the existing CONNECT gateway. Upstream continuation URLs are validated, never followed. Repository `:latest` suggestions do not prove that the tag/platform exists; only Alpine candidates are eligible for the existing authoritative scan admission, with CVE availability conditional on the server DB.

The returned `policy` publishes the enforced bounds: 12 upstream records/page, at most 5 pages/60 unique candidates; 128,000 raw bytes/page and 640,000 bytes/generation; a 5,000ms absolute discovery deadline spanning CONNECT, TLS, headers and body, and 25,000ms cumulative upstream time; 300,000ms idle cursor expiry; 8 active requests per API process and 2 per subject; 30 calls per subject per 60,000ms window (including cursor retries); at most 1,024 discovery sessions and 1,024 rate entries. These are **process-local** limits in one controller's session manager, not distributed/global quotas across replicas. Capacity rejects with 429 rather than clearing live rate state. Existing OCI transfer timeouts are not shortened to discovery deadlines.

Cursors are random, server-owned, and bound to subject, normalized query/inferred mode/repository and generation. The latest consumed cursor can replay its cached response without another upstream call; superseded/tampered cursors fail closed. Restarting the API loses ephemeral sessions: a prior cursor returns 410 `IMAGE_SEARCH_EXPIRED`, not a successful empty/terminal result. A failed upstream attempt returns 503 `IMAGE_SEARCH_UNAVAILABLE` and retires that generation, so reusing its continuation returns 410 without upstream I/O. Recovery starts a new generation/page one **without** the old cursor. The browser retains loaded candidates/selected scan intent as incomplete during recovery, replaces rather than merges prior-generation results on success, and distinguishes terminal empty results from errors and quota exhaustion. This does not change POST idempotency, durable scan state, Alpine admission or generic-image support.

The transport regression test uses `openssl` to generate a disposable certificate in the OS temporary directory and trusts it only in isolated child processes via `NODE_EXTRA_CA_CERTS`. Loopback CONNECT/TLS fixtures verify stalled headers, continuously dripping/oversized bodies, untrusted/wrong-host rejection and socket/timer cleanup. Production TLS verification is unchanged; these controlled tests are not live Hub or deployment evidence.

## Optional demo account (separate from scan authorization)

`AUTH_DB_PATH` must point to a persistent, writable SQLite file outside the scan ledger (`SCAN_LEDGER_PATH`); missing/invalid storage fails closed. `AUTH_ORIGIN` must equal the public browser origin exactly (e.g. `http://127.0.0.1:5173` for local testing). HTTPS is required except when `AUTH_ALLOW_INSECURE_LOCAL_HTTP=true` and the configured origin is loopback. The auth API provides `POST /api/v1/auth/register`, `/login`, `/logout`, and `GET /me`. Mutations require a matching `Origin` and JSON; sessions use an HttpOnly SameSite=Lax cookie (Secure on HTTPS), expire after seven days and are revoked on logout. Passwords use salted scrypt; login/register attempts are limited by email and socket IP in persistent SQLite. Place the database in an access-controlled volume and protect it with normal backups; do not commit it or publish this API as-is.

For an easy local-only check, run `pnpm dev:auth` from the repository root, then visit `http://127.0.0.1:5173/register`; see the root README for steps. It creates an ignored persistent `.local-auth/auth.sqlite` and starts both services on loopback; Ctrl+C stops both. For a **manual launch instead**, start the API with `SCAN_BIND_ADDRESS=127.0.0.1`, `PORT=3001`, a unique 32+ byte `SCAN_JWT_SECRET`, `SCAN_JWT_ISSUER`, `SCAN_JWT_AUDIENCE`, `AUTH_DB_PATH` (outside the repo), `AUTH_ORIGIN=http://127.0.0.1:5173`, and `AUTH_ALLOW_INSECURE_LOCAL_HTTP=true`, then run Vite with `AUTH_DEV_PROXY_TARGET=http://127.0.0.1:3001 pnpm dev -- --host 127.0.0.1`. Generate the secret locally; do not put it in a tracked `.env` file. The Vite dev proxy forwards only `/api/v1/auth`: live `/scans` requires the separate assembled Docker stand. If the proxy is unset, `/` and `/demo/scans/*` still work with fixtures; registration requires a separately configured same-origin auth ingress. A public deployment needs an audited HTTPS reverse proxy, abuse protections and isolated persistent volumes; the Vite dev proxy is not production infrastructure. An account cookie alone never grants a scan: the local browser controller checks operator-enrolled immutable account IDs (`SCAN_BROWSER_ALLOWED_USER_IDS`), while the internal JWT endpoints remain unavailable to the browser.

## Authenticated read surface (internal network only)

`GET /api/v1/scans/:scanId` returns the subject's state, pinned digest/platform and sanitized result (404 for absent/foreign ID). `GET /api/v1/scans?limit=50` additionally requires `scan:list` alongside the JWT's existing `scan:create` scope and returns `{scans, nextCursor}`: subject-scoped records ordered by durable insertion, with a bounded keyset cursor `bound:lastEventSeq` (monotonic persisted event IDs, safe across retention pruning), no idempotency key, and 1–100 records per page. Pass `nextCursor` verbatim as `cursor` until null; malformed pagination returns 400. The local stand serves the same subject-scoped list/status/results over the separate `/api/v1/browser/scans` cookie controller for explicitly enrolled account IDs; it does not proxy this internal JWT endpoint. Never expose `SCAN_JWT_SECRET` or a shared token in frontend code, localStorage, URL, or Vite environment variables; see `../deploy/README.md`. `GET /:scanId/events` is a bounded live SSE stream for the owner: durable event IDs, exclusive `Last-Event-ID` replay, 15-second heartbeat, 120-second stream lifetime, per-process limits of 64 connections total and 6 per subject. Terminal reconnect after its last ID contains no duplicate scan event; clients fetch GET status as the authoritative snapshot. Disconnect cleans up the stream; clients may reconnect. `POST /:scanId/cancel` requires `scan:cancel` (the internal JWT verifier also requires `scan:create`); the browser controller requires an enrolled cookie, matching Origin and empty JSON body. Cancellation atomically makes queued/running work terminal in the ledger and fences late results; it is not a promise that the OS process already stopped. Full CVE/SBOM are not implemented.
