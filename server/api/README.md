# Scan API — fail-closed scaffold

`pnpm --filter @diplom/scan-api test` and `pnpm --filter @diplom/scan-api typecheck` (Node 23.11 was used for validation).

`src/app.module.ts` imports `ScansModule`, which composes `SecurityModule`, `OciModule` and `LedgerModule`; `src/main.ts` is only the HTTP bootstrap. `src/worker/` is separate from the HTTP module and is not deployed or invoked yet. NestJS constructor dependencies use explicit `@Inject` tokens so the tsx runtime resolves providers consistently.

`src/ledger/ledger.ts` uses Drizzle ORM with `better-sqlite3` and persists immutable pinned targets and an outbox in one `BEGIN IMMEDIATE` transaction. The versioned migration preserves existing v1/v2 rows; `claim` uses expiring leases/attempts, `finish` rejects stale acknowledgements, `retry` schedules another attempt, and `prune` removes terminal rows after 30 days. Tests exercise migration, rollback, backup/restore with WAL, concurrent connections, restart, stale ack and replay. No server loop invokes these methods yet. See `src/ledger/README.md` before deployment. Pin and validate a supported Node LTS and native addon build on a clean CI install; use one persistent SQLite volume, never an ephemeral container filesystem.

The NestJS POST route **does not enqueue or return 202**. Startup requires a dedicated `SCAN_JWT_SECRET` (at least 32 bytes), `SCAN_JWT_ISSUER`, `SCAN_JWT_AUDIENCE`; signed HS256 JWT must carry `sub`, `iat`, short `exp` and `scan:create` scope. Never reuse a single API token as user identity; protect these secrets outside the repository. Unauthorized requests return 401, authorized requests 503. The route binds only to 127.0.0.1. `src/scans/image-reference.ts` rejects ambiguous/untrusted names. `src/oci/registry-resolver.ts` verifies index/child SHA256 and exact platform through an explicit CONNECT gateway; redirects/auth challenges and direct bare manifests currently fail closed (config blob/platform and token policy not complete). `src/worker/scan-worker.ts` constructs a digest-only Trivy command with remote source, no inherited Docker env and sanitized failure codes; this module is **not wired to a running worker** and cannot enforce a network boundary by itself. No raw scanner findings or stderr should be persisted or exposed.

Before enabling 202: deploy and verify an independently enforced production gateway and scanner network isolation (NOT the lab `LAB_FIXTURE`/self-signed TLS/`--insecure`), complete manifest config/blob/platform validation and trusted token flow, integrate authenticated request parsing/replay → resolver → SQLite → worker with readiness checks and response handling, verify safe DB availability and normalized findings, and run end-to-end positive/negative tests. The TLS registry in `../security-lab/` is a lab fixture **not** a production gateway.
