# Scan ledger (SQLite user_version 2)

`ledger.ts` is the **only** schema migrator; `schema.ts` maps the existing v2 tables for Drizzle queries, not for `drizzle-kit push`. Do not run `push` on a populated volume or initialize Drizzle's migration journal separately. This is single-instance durable storage, not a replacement for worker/egress readiness.

- v1: `scans(id TEXT PRIMARY KEY, subject TEXT NOT NULL, idempotency_key TEXT NOT NULL, registry TEXT NOT NULL, repository TEXT NOT NULL, digest TEXT NOT NULL, platform TEXT NOT NULL, state TEXT NOT NULL CHECK(state IN ('queued','running','completed','failed','cancelled')), created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP, UNIQUE(subject,idempotency_key))`; `outbox(scan_id TEXT PRIMARY KEY REFERENCES scans(id), delivered_at TEXT)`.
- v2: v1 plus nullable `scans.fingerprint`, `scans.terminal_at`, `scans.checks TEXT NOT NULL DEFAULT '[]'`, `scans.scope TEXT NOT NULL DEFAULT 'image'`; `outbox.attempts INTEGER NOT NULL DEFAULT 0`, nullable `outbox.lease_until`, `outbox.next_run_at INTEGER NOT NULL DEFAULT 0`. Names, existing values and SQLite `user_version=2` remain unchanged. Fresh v0 databases create v1 then migrate in one `BEGIN IMMEDIATE`; a nonempty unversioned DB, incomplete v1 schema, or version >2 fails closed. Existing v2 is not altered.
- Each connection enables `WAL`, `foreign_keys=ON`, and a 5000ms busy timeout. `enqueue`, `claim`, `finish`, and retention use short synchronous `BEGIN IMMEDIATE` transactions; never run network/async work inside them. Outbox is at-least-once with attempt-number fencing, not exactly-once delivery. Keep `SCAN_LEDGER_PATH` on a persistent writable volume; its absence must not fall back to an in-memory store.

Before deploying a driver/runtime change: stop writers or make a **consistent online backup** with SQLite's backup API (not just copying the main file while WAL is active). Restrict backup file permissions: it contains subjects and scan metadata. Restore to a separate file, check `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, `PRAGMA user_version`, row counts and representative rows, then exercise the v1/v2 fixture migration tests on that copy. Keep the original DB/WAL/SHM until verification succeeds. On SQLite errors, do not serve success or reinitialize storage.

`better-sqlite3` is a native addon: clean installs must explicitly permit/build it in pnpm 10's workspace build policy and test the binary on the chosen Node 22/24 LTS and deployment image. Local Node 23 builds do not prove LTS compatibility. `drizzle-kit` is installed for future reviewed, versioned migrations; do not run auto-sync against this baseline.
