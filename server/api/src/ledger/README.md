# Scan ledger (SQLite user_version 15 — source, not deployed)

## Current cancellation and deployment boundary

v15 adds `outbox.lease_token` and bounded `scan_checkpoints`. A completed, validated, sanitized check may be checkpointed under its original current claim. Cancellation atomically publishes only these committed checks, acknowledges/revokes the outbox and emits one terminal event; the state remains **cancelled**, even with retained findings. Unfinished checks remain absent/unknown, never checked zero. No raw or in-memory fragments are published. Prior CVE DB evidence/timestamps remain historical; cancellation does not refresh them.

All terminal writers and retry require the original claim token as well as a current attempt and live lease. Replacement/retry revoke older checkpoints. Migrated running rows receive no invented token and must be reclaimed. Checkpoint storage exceptions propagate rather than becoming fabricated scanner failures; a previously committed sibling can still be retained by subsequent cancellation. Ordinary/config/archive paths and owner HTTP/browser reads are covered by disposable tests and a separate ledger/worker re-review.

**Do not deploy this migration alongside old writers.** Existing live volumes were not migrated. Stop admissions and all old writers, make and verify a consistent compatible backup, then coordinate the v15 API/worker rollout. Rollback requires a compatible binary or verified pre-migration restore, never an old binary against v15. See `docs/partial-cancel-implementation-20261016.md`, `docs/partial-cancel-independent-review-20261016.md` and `docs/partial-cancel-http-ui-20261016.md`.

## Historical schema/proof notes

The following v1–v11 notes and dated proof descriptions explain their original behavior; statements about discarded in-memory intermediate checks are historical, not the v15 checkpoint contract.

`ledger.ts` is the **only** schema migrator; `schema.ts` maps the unchanged scans/outbox tables for Drizzle queries, not for `drizzle-kit push`. Do not run `push` on a populated volume or initialize Drizzle's migration journal separately. This is single-instance durable storage, not a replacement for worker/egress readiness.

- v1: `scans(id TEXT PRIMARY KEY, subject TEXT NOT NULL, idempotency_key TEXT NOT NULL, registry TEXT NOT NULL, repository TEXT NOT NULL, digest TEXT NOT NULL, platform TEXT NOT NULL, state TEXT NOT NULL CHECK(state IN ('queued','running','completed','failed','cancelled')), created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP, UNIQUE(subject,idempotency_key))`; `outbox(scan_id TEXT PRIMARY KEY REFERENCES scans(id), delivered_at TEXT)`.
- v2: v1 plus nullable `scans.fingerprint`, `scans.terminal_at`, `scans.checks TEXT NOT NULL DEFAULT '[]'`, `scans.scope TEXT NOT NULL DEFAULT 'image'`; `outbox.attempts INTEGER NOT NULL DEFAULT 0`, nullable `outbox.lease_until`, `outbox.next_run_at INTEGER NOT NULL DEFAULT 0`. Names, existing values and SQLite `user_version=2` remain unchanged. Fresh v0 databases create v1 then migrate in one `BEGIN IMMEDIATE`; a nonempty unversioned DB, incomplete v1 schema, or future version fails closed. Existing v2 rows survive upgrades.
- v3: `scan_results` originally stored only the count/coverage. v4: durable per-subject fixed-minute admission counters. v5: bounded allowlisted secret findings, per-check outcome/error code, scanner version, and persisted monotonic scan event IDs. Existing v3 count-only results migrate with `outcome=unsupported`, not a claim that individual findings were retained. v6: bounded decision audit (subject or anonymous, target category, scope, allowlisted reason, optional scanId); no bearer/raw scanner URLs. Accepted-job audit and outbox insert share the enqueue transaction. `prune(30)` deletes terminal scans and related rows, stale rate counters and old audit entries; outbox leases stay fenced.
- v7 adds SBOM coverage/components; v8 adds vulnerability coverage/findings; v9 adds independent combined-check outcomes and `partial`. v10 adds `scan_archive_results(scan_id PRIMARY KEY REFERENCES scans(id), attempt, report)`: a bounded, strictly validated exact-nginx-candidate receipt/result envelope. It is written with the delivered outbox lease, terminal state and event in one attempt-fenced transaction. This is closed qualification storage, **not public nginx admission**; both exact candidates remain unqualified. The old candidate is OS_EOL; the separately pinned Alpine 3.23.3 candidate has dated positive OS-CVE/SBOM consumer and combined DOM evidence, not production admission or remote npm qualification. Legacy rows are not rewritten or upgraded to archive/DB provenance. Owner-scoped API projections retain separate OS/Node outcomes and the actual verified DB identity; retention includes the new table.
- v11 adds `scan_check_results`, keyed by `(scan_id,check_name)` (currently config only), with positive attempt, exact image-config checks/policy versions, outcome and a ≤16384 UTF-8 byte closed report. No historical rows are backfilled: legacy scans do not gain invented v1 coverage. Upgraded consumers persist config skipped when unselected; selected config has a separate outcome. Sibling results, config, outbox acknowledgement, terminal state and one event commit or roll back together. Verification/network/hash work remains outside the transaction. Both capability issuance and config-inclusive finalization require running/current attempt, undelivered outbox and **non-NULL lease**: `retry()` clears the lease without incrementing attempts, revoking authority. This is not a new claim that legacy `attemptActive()` checks clock expiry. Selected-config claims reserve an additional 31s; legacy timing is unchanged. Cancellation publishes no in-memory intermediate results.
- Do not roll a v11 volume back to a v10 binary in place: older binaries reject future schemas. Before deployment, make/verify a consistent backup; rollback uses a compatible binary or a verified pre-migration copy. The live stand was not migrated by the disposable archive proof.
- Nginx archive claim reserves the unchanged627s lease. The 1GiB/no-swap disposable memory proof creates actual cookie HTTP jobs: killing only the CVE scanner preserves prior in-memory Secrets/SBOM in one final partial transaction; killing the entire worker does **not** persist those intermediate checks. Real restart waits for the lease, writes only attempt2, rejects attempt1 and produces one terminal report/event. Persistent ledger/RO DB survive while container tmpfs resets; actual generated-tree recovery is tested separately. Injector OOM is not whole-parent OOM proof. Current resource/hash-buffer proofs still require fresh independent reviews; default production nginx remains closed (recipe/evidence: `server/deploy/proof/nginx-dom.md`).
- SSE is short-lived, subject-scoped ordered replay of persisted transitions with Last-Event-ID and a terminal snapshot fallback, **not** an open live push/periodic heartbeat. Clients reconnect/refetch status; do not advertise live streaming until implemented.
- Each connection enables `WAL`, `foreign_keys=ON`, and a 5000ms busy timeout. `enqueue`, `claim`, `finish`, and retention use short synchronous `BEGIN IMMEDIATE` transactions; never run network/async work inside them. Outbox is at-least-once with attempt-number fencing, not exactly-once delivery. Keep `SCAN_LEDGER_PATH` on a persistent writable volume; its absence must not fall back to an in-memory store.

Before deploying a driver/runtime change: stop writers or make a **consistent online backup** with SQLite's backup API (not just copying the main file while WAL is active). Restrict backup file permissions: it contains subjects and scan metadata. Restore to a separate file, check `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, `PRAGMA user_version`, row counts and representative rows, then exercise the v1/v2/v3 fixture migration tests on that copy. Keep the original DB/WAL/SHM until verification succeeds. On SQLite errors, do not serve success or reinitialize storage.

`better-sqlite3` is a native addon: clean installs must explicitly permit/build it in pnpm 10's workspace build policy and test the binary on the chosen Node 22/24 LTS and deployment image. Local Node 23 builds do not prove LTS compatibility. `drizzle-kit` is installed for future reviewed, versioned migrations; do not run auto-sync against this baseline.
