# ТЗ: анализ безопасности Docker-образов и локальных контейнеров

> **Черновик для нового согласования.** Прежний прогон Flownix `DIP-HRNS-1` (`c26a4e2e-f9e3-4456-8af9-f4f7f106b47e`) и его запрос на создание задач по старой версии ТЗ отклонены. Новый прогон `583713b5-d3de-459c-abb1-45947dc2181f` учитывает актуальное ТЗ, включая RareUI/Canvas UI и раздельные бюджеты токенов продукта и агентов. **Новое одобрение человека ожидается; задачи ещё не созданы.** Наличие файла не означает утверждения ТЗ или реализации описанных функций.

## Purpose
Спроектировать веб-приложение для проверяемого анализа безопасности OCI-образов и, при отдельном разрешении, локальных контейнеров Docker. Это проектируемое поведение, а не описание существующего backend: сейчас есть React/Vite-каркас и README сервера. Отчёт никогда не означает «уязвимостей нет вне проверенного покрытия».

## Границы и приоритеты
P0 — MVP: image scan из разрешённого registry, digest/platform, Trivy vulnerability/secrets/SBOM, асинхронные задания, авторизованные результаты, coverage, прогресс и UI. P1 — включаемые image metadata/config checks, изолированный container inspect по согласию, LLM-сводка и связанный чат. P2 — host baseline, Dockerfile/IaC по переданному исходнику, Cosign, Syft, сравнение сканов, VEX. P1/P2 не считаются выполненными без указанных прав, источников и тестов. Варианты OCI archive/layout, local image и Docker Bench — только после отдельного PoC и оценки лицензии/ресурсов.

## Матрица охвата
| Класс проверки | Image (registry digest/platform) | Локальный container (ID+snapshot, opt-in) | Host/daemon (отдельный opt-in) |
|---|---|---|---|
| CVE OS/Node packages | Trivy image, версия DB и источник advisory | findings закреплённого image + снимок конфигурации; writable layer не проверен | не применимо |
| Secrets | Trivy image, значения редактируются | inspect без env/значений секретов; файлы томов не читаются | не применимо |
| SBOM | Trivy image; Syft только после PoC | SBOM образа, не writable layer | не применимо |
| Image metadata/config | явный флаг проверок OCI metadata/history | наследуемая конфигурация образа, не Dockerfile | не применимо |
| Runtime configuration | неприменимо | inspect: user, privileged, caps, seccomp/AppArmor, namespaces, mounts/socket, ports/network, read-only rootfs, resources | неприменимо |
| Host baseline | неприменимо | неприменимо | согласованные read-only факты; Docker Bench/CIS после PoC |
| Dockerfile/IaC | лишь по отдельно переданному источнику | не восстанавливается из history | не применимо |
| Подпись/attestation | Cosign по доверенной identity/issuer или ключу после PoC | наследует проверку digest образа | не применимо |

Каждая применимая ячейка получает `checked|unsupported|not_authorized|failed|skipped` с reason и версией checks. `checked` означает выполненную проверку, не безопасность. Исходные scanner results недоверенны.

## Предлагаемый контракт реализации
NestJS + TypeScript: авторизованный HTTP API, отдельный ограниченный worker и адаптеры OCI registry/Trivy; локальный daemon доступен только отдельному доверенному broker с allowlist inspect и ID; не в публичном API и не в браузере. Предлагаемые маршруты `POST /api/v1/scans` (image reference либо container ID, scope/checks/idempotencyKey) → 202 `{scanId,statusUrl,eventsUrl}`, `GET /api/v1/scans/:id`, `/events` (SSE, ID, Last-Event-ID, heartbeat, replay или snapshot), `/results` (страницы findings+coverage), `POST /api/v1/scans/:id/cancel`; `GET /api/v1/scans` для списка. `queued→running→completed|partial|failed|cancelled`; `running→cancelling→cancelled|partial|failed`. Terminal состояния неизменяемы. Event `{id,scanId,state,stage,completed,total,percent|null,updatedAt,errorCode?}`; процент null при неизвестном total. Выбор durable job ledger/хранилища, миграций и retention до реализации: single-instance durable local вариант ~2–4 дня; многорепличный DB+queue/pubsub — новая инфраструктура и ориентировочно +5–10 дней, оценка уточняется. In-memory не единственный источник состояния.

Нормализованная находка: finding_id, target digest/platform либо container ID+hash санитизированного snapshot/time, категория, rule/CVE, purl/ecosystem, версия/место, severity + источник, installed/fixed version, fix-state, scanner/version, DB/checks timestamp, provenance/evidence_ref (без секрета), рекомендации; дубли объединять с сохранением provenance. Raw outputs не передавать в UI/LLM. Ошибки отдельных scanners делают итог `partial`, не «0 проблем».

UI: React 19 + TypeScript/Vite, app→pages→features→shared, локальные shadcn/ui primitives поверх Radix/Tailwind: Button/Card/Badge/Tabs/Progress/Skeleton/Alert/AlertDialog/Sheet/Table/Sonner. Маршруты список→запуск→деталь (этапы, находки, покрытие, чат); на mobile одна колонка и фильтры Sheet. TanStack Query по scanId/фильтрам, сверка snapshot после SSE reconnect; лениво загружаемый renderer fenced code, текстовый fallback, без raw HTML. Admin-shell не требуется.

Дополнительные источники UI: [RareUI](https://www.rareui.com/) и [Canvas UI](https://canvasui.dev/docs) наряду с shadcn/ui. Их элементы выбираются точечно под визуальную задачу, а не добавляются оптом: перед использованием проверяются лицензия, совместимость с React 19/Tailwind 4, доступность, производительность, безопасность стороннего кода и размер бандла; общий дизайн-язык (токены цветов, типографика, радиусы, фокус) остаётся единым. Canvas UI документирует React-варианты canvas-эффектов и shadcn registry, но часть возможностей опирается на экспериментальный `html-in-canvas`: использовать только для необязательных декоративных эффектов, с обычным HTML-fallback, поддержкой `prefers-reduced-motion` и без сокрытия результатов сканирования, ошибок или управления. Возможности RareUI не подтверждены из-за блокировки доступа к сайту; конкретные компоненты и условия использования выбираются после проверки документации. На дату ТЗ ни RareUI, ни Canvas UI в проект не установлены.

ИИ: NestJS порт LlmProvider с серверными credentials; выбран OpenRouter, конкретная модель ещё не выбрана. Ключ берётся только из серверного окружения `OPENROUTER_API_KEY` и не хранится в ТЗ, Flownix, клиентском бандле или логах. Только авторизованные нормализованные findings+coverage, редактированные evidence и история текущего scan; лимиты токенов/затрат/таймаут и явная политика согласия на передачу внешнему провайдеру. ИИ объясняет, но не доказывает: finding_id валидируется сервером, неподтверждённые утверждения отмечены гипотезой. Сводка/история и потоковый чат (delta/citation/usage/done/error) — проектируемый API, не реализованный факт.

Экономия токенов продукта: формировать контекст по релевантным finding_id и компактным очищенным evidence вместо полного отчёта, версионировать краткую историю беседы, ограничивать длину вопроса, историю, `max_output_tokens` и бюджет пользователя/скана; сохранять ссылки на исходные находки, ограничения покрытия и важные решения при сжатии. Кэшировать повторную сводку только для того же разрешённого scan, версии findings, модели, версии промпта и политики доступа, не переиспользуя чужие данные. Учитывать реальные input/output tokens и оценочную стоимость из метрик провайдера, сравнивать её с бюджетом, предупреждать до дорогого вызова, останавливать генерацию при достижении лимита и оставлять отчёт сканеров доступным. Экономия не должна приводить к пропущенным critical находкам или сокрытию неполного coverage.

Экономия токенов при разработке через Flownix — отдельный процесс от расходов ИИ-чата: поэтапно выдавать агентам только нужный контекст, короткие структурированные результаты и релевантные OpenSpec-разделы; отсекать большие `flow_nodes` в промежуточных шагах и задавать `max_tokens` контекстной политики харнесса, версии и роли. Добавить явные ограничения `max_tokens`/`max_cost_usd` и требование передавать usage при `work.complete`/`work.fail`, а также отслеживать фактический расход в панели провайдера: Flownix считает токены и стоимость прогона только по сообщённому агентами usage, поэтому это **не гарантированный жёсткий лимит расходов провайдера**. Рассмотреть отдельный локальный агентский скилл `token-efficient-spec` для коротких ролей, выборочной загрузки скиллов, компактных выходов и запрета повторного чтения неизменившегося контекста. Перед подключением стороннего скилла проверить источник, лицензию и инструкции; скилл направляет поведение агента, но не ограничивает счета за API самостоятельно. Для действующего опубликованного харнесса это потребует новой версии или клона, текущий ожидающий одобрения прогон не меняется.

## Requirements

### Requirement: Авторизованный запуск image scan [P0]
Система SHALL создавать асинхронную проверку только разрешённого registry image без обращения к Docker daemon и закреплять фактические digest и platform.
#### Scenario: Изменяемый tag
- GIVEN пользователь с правом image scan выбрал разрешённый tag
- WHEN API создаёт задание и разрешает manifest
- THEN ответ 202 содержит scanId и итог закреплён за фактическим digest/platform, а не только tag.

### Requirement: Защита registry egress [P0]
Система SHALL проверять registry allowlist, фактические DNS-адреса и redirects с запретом loopback, link-local, metadata и приватных адресов вне утверждённой политики.
#### Scenario: Перенаправление на внутренний адрес
- GIVEN разрешённый registry возвращает redirect на metadata IP
- WHEN worker получает manifest
- THEN запрос блокируется и выдаёт безопасную ошибку без раскрытия токенов.

### Requirement: Покрытие image checks [P0]
Система SHALL отражать отдельный исход vulnerability OS/Node, secrets и SBOM с версиями scanner/DB и причиной неполноты.
#### Scenario: Нет базы уязвимостей
- GIVEN vulnerability DB недоступна, а secrets check прошла
- WHEN завершается скан
- THEN CVE получает `failed` с причиной, secrets — `checked`, а отчёт `partial`, а не «0 CVE».

### Requirement: Дополнительные image checks [P1]
Система SHALL запускать проверки image metadata/config только по явному выбору и не выдавать OCI history за полный Dockerfile.
#### Scenario: Dockerfile отсутствует
- GIVEN предоставлен лишь digest образа и image-config проверка выключена
- WHEN показывается coverage
- THEN metadata/config помечен `skipped`, Dockerfile/IaC `unsupported` и ни один из них не объявлен проверенным.

### Requirement: Допуск к container snapshot [P1]
Система SHALL разрешать inspect только конкретного container ID после отдельного согласия и серверной проверки scope и только через ограниченный broker; при отсутствии безопасной границы отказывать.
#### Scenario: Доступен лишь docker.sock read-only mount
- GIVEN broker не умеет запрещать exec/create/export, а socket примонтирован с `:ro`
- WHEN пользователь запрашивает container scan
- THEN запрос отклоняется до обращения к Engine и отказ аудируется.

### Requirement: Честная граница container check [P1]
Система SHALL привязывать findings runtime config к container ID, daemon/context и времени/hash очищенного inspect snapshot и явно исключать writable layer, volumes и traffic.
#### Scenario: Контейнер изменился после snapshot
- GIVEN снимок создан до изменения настроек контейнера
- WHEN пользователь просматривает старый отчёт
- THEN время снимка и исторический характер данных видны, а текущая безопасность не утверждается.

### Requirement: Изолированный host baseline [P2]
Система SHALL запускать только согласованные host/daemon read-only checks после независимого opt-in и явно отмечать недоступные из-за прав проверки.
#### Scenario: Host opt-in не дан
- GIVEN запущен scan image или container без разрешения host
- WHEN формируется отчёт
- THEN host checks не выполняются и получают `not_authorized`, а не «прошли».

### Requirement: Нормализация и происхождение [P0]
Система SHALL дедуплицировать совпадающие findings без потери scanner provenance и показывать severity source, версии DB/checks и evidence_ref без значения обнаруженного секрета.
#### Scenario: Два scanner evidence одного CVE
- GIVEN два источника дали совпадающий CVE для того же digest, пакета, версии и места
- WHEN строится отчёт
- THEN создана одна finding с двумя provenance, без утраты evidence.

### Requirement: Жизненный цикл и поток прогресса [P0]
Система SHALL возвращать согласованные terminal states и SSE события с упорядоченным ID, snapshot/replay при reconnect и percent=null при неизмеримом прогрессе.
#### Scenario: Переподключение
- GIVEN клиент видел событие N и потерял соединение
- WHEN он переподключается с Last-Event-ID=N
- THEN получает упорядоченные новые события либо актуальный снимок при истёкшей истории, без фиктивных процентов.

### Requirement: Идемпотентность и отмена [P0]
Система SHALL ограничивать параллельные задания и идемпотентно обрабатывать повторный запуск и отмену с сохранением неполных результатов.
#### Scenario: Повтор и отмена
- GIVEN пользователь повторяет запрос с тем же idempotencyKey и затем отменяет работающий scan
- WHEN операции завершены
- THEN второй scan не создаётся, новые стадии не стартуют, итог `cancelled` либо `partial` обоснован и терминален.

### Requirement: Разграничение результатов [P0]
Система SHALL повторно проверять авторизацию на status, events и пагинированные results, не раскрывая наличие чужих сканов.
#### Scenario: Чужой scanId
- GIVEN пользователь не владеет scanId
- WHEN он запрашивает статус, поток или результаты
- THEN данные и существование приватного задания не раскрываются и LLM не вызывается.

### Requirement: Интерфейс сканирования [P0]
Интерфейс SHALL показывать цель, подтверждённый scope, этап, неполноту, находки и coverage с различением «0 findings», «нет совпадений фильтра» и «не проверено».
#### Scenario: Фильтр без совпадений
- GIVEN в отчёте есть findings и выбран фильтр без совпадений
- WHEN пользователь открывает результаты
- THEN показывается «нет совпадений» со сбросом фильтра, а coverage остаётся видимым.

### Requirement: Устойчивый доступный UI [P1]
Интерфейс SHALL поддерживать мобильную одну колонку, клавиатуру и видимый фокус, текстовые статусы и дозированный aria-live без автоскролла против воли пользователя.
#### Scenario: Поток на мобильном устройстве
- GIVEN открыт скан на узком экране с screen reader
- WHEN часто приходят progress events
- THEN фокус не сбрасывается, объявляются смена этапа/итог, а токены и каждое событие не озвучиваются.

### Requirement: Дополнительные UI-компоненты и деградация эффектов [P1]
Интерфейс SHALL допускать точечное использование совместимых компонентов RareUI и Canvas UI при сохранении единого дизайн-языка, доступности и полноценной работы без необязательных canvas-эффектов.
#### Scenario: Нет поддержки canvas-эффекта
- GIVEN браузер не поддерживает необходимую графическую возможность либо включён режим уменьшения анимации
- WHEN пользователь открывает экран проверки или результатов
- THEN содержимое, управление, статусы и находки остаются доступны в обычном HTML без обязательной анимации и без потери фокуса.

### Requirement: Авторизованная ИИ-сводка [P1]
Система SHALL создавать сводку только из разрешённых очищенных findings и coverage доступного пользователю scan, проверять finding_id в утверждениях и маркировать гипотезы.
#### Scenario: Модель ссылается на отсутствующую находку
- GIVEN провайдер ответил с неизвестным finding_id
- WHEN сервер проверяет сводку
- THEN ссылка не публикуется как факт, а неопределённость явно указана.

### Requirement: Контекстный чат [P1]
Система SHALL хранить ограниченную историю отдельно для каждого scanId и пользователя и передавать события delta/citation/done/error с отменой генерации и квотами.
#### Scenario: Переключение scan
- GIVEN пользователь переписывался по скану A
- WHEN он открывает чат скана B
- THEN история A не оказывается в контексте B; при сбое LLM детерминированные findings доступны.

### Requirement: Экономный контекст ИИ без потери доказательств [P1]
Система SHALL ограничивать объём передаваемого в LLM контекста, историю и длину ответа в пределах настроенного бюджета, сохраняя важные находки, их `finding_id` и сведения о неполном покрытии.
#### Scenario: Большой отчёт и длинный чат
- GIVEN скан содержит много находок, в том числе critical, и длинную историю сообщений
- WHEN пользователь задаёт вопрос о конкретной проблеме
- THEN модель получает только разрешённый релевантный контекст и компактную историю, при этом critical находки, ссылки на исходные результаты и ограничения coverage не теряются.

### Requirement: Измерение и ограничение стоимости ИИ [P1]
Система SHALL учитывать входные и выходные токены и ориентировочную стоимость генерации, предупреждать о приближении к настроенному лимиту и запрещать новую генерацию при исчерпанном бюджете без сокрытия результатов сканеров.
#### Scenario: Бюджет исчерпан
- GIVEN пользователь достиг настроенного лимита токенов или стоимости ИИ
- WHEN он запрашивает новую сводку или сообщение чата
- THEN вызов провайдера не выполняется, показывается причина отказа и остаются доступны исходные findings и coverage.

### Requirement: Безопасный Markdown [P1]
Интерфейс SHALL отображать потоковый Markdown с fenced code без выполнения HTML, JS или команд и разрешать только безопасные URL-схемы.
#### Scenario: Опасный неполный fenced block
- GIVEN провайдер прислал HTML/script и javascript: URL в незавершённом Markdown
- WHEN UI рендерит поток
- THEN скрипт и HTML не исполняются, ссылка не активна, код читаем текстом.

### Requirement: Аудит и конфиденциальность [P0]
Система SHALL сохранять аудит субъект/цель/scope/решение/время и применять allowlist полей к логам, ответам и LLM, исключая токены, raw env и inspect secrets.
#### Scenario: Отказ или секрет в сканере
- GIVEN denied host scan либо найден токен в output scanner
- WHEN пишется аудит и готовится отчёт
- THEN видны причина и безопасный тип/место, но нет значения токена или credentials.

## Приёмка и решения
Приёмка: контрактные тесты API/authz/idempotency/SSE-reconnect/cancel; фикстуры Trivy success/failure/stale DB и дубликатов; отрицательные Docker broker тесты exec/create/другой ID/`:ro`; SSRF/DNS redirect, resource limits и redaction; UI e2e desktop/mobile/keyboard/aria-live, fallback Canvas UI и XSS на частичных fences; LLM fake provider: чужой scanId, prompt injection, несуществующие citations, timeout/usage, длинная история, достижение бюджета, сохранение critical findings после сжатия и отсутствие межпользовательского кэша. Безопасность не доказывается числом нулевых находок; критерий — честное coverage и отказ без разрешения.
Требует решения человека до интеграции: конкретная модель OpenRouter, политика региона/retention/бюджета и согласие на передачу внешнему LLM (ключ хранится только в серверном окружении); доступ к daemon/context и утверждение broker-модели угроз; host scan и необходимые полномочия; выбор durable storage/job ledger и режим single/multi-instance; лицензия/PoC дополнительных scanners.

## Non-goals
- Не обещать «все параметры», анализ реального трафика, writable layers, volumes, эксплуатацию CVE или отсутствие всех уязвимостей.
- Не давать браузеру/публичному API Docker socket; mount `:ro`, SSH/TLS сами по себе не ограничивают команды Engine.
- Не переносить код, токены и URL исходного продукта; не запускать host checks по умолчанию.
