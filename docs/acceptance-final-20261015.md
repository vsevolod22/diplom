### Важная разница критериев отмены

Нельзя считать требование сохранности частичных результатов выполненным потому, что cancelled report честно пуст. Но найденные implementation docs указывают на **вероятно намеренное сужение целостности/безопасности**, а не на доказанный случайный UI regression: `server/api/src/ledger/README.md:9` прямо говорит «Cancellation publishes no in-memory intermediate results» и описывает общий attempt-fenced commit/rollback sibling results, config, outbox, terminal state/event. Там же `:11` различает CVE-child failure с сохранением независимых Secrets/SBOM в final partial transaction и whole-worker kill без durable intermediate checks. `server/api/README.md:9,31` запрещает raw scanner findings/stderr и документирует terminal cancel/late-result fencing, не гарантируя мгновенный OS stop. Эти README — implementation handoffs, не доказательство applied spec; отдельные их SSE/CVE описания устарели, поэтому целиком как current contract они не принимаются.

`docs/task16-chat-ui.md:83–87` и `server/api/src/llm/TASK14.md:148–152` отдельно запрещают публикацию partial LLM frames до полного done/EOF/current durable validation; при chat failure уже существующие scanner findings остаются вне панели. Это сходный security principle, **не waiver scanner partial-cancel AC**. В локальных DOC10/source39/source41 saved-report specs cancellation означает сброс/отмену старого GET при смене контекста, не отмену scanner job. Ранее reported applied DOC10 v3 не переопределяет глобальное cancellation требование DOC1/DOC2/ТЗ. Подтверждённой applied delta именно на scanner cancellation exception в просмотренных локальных docs не найдено; текущая remote history неизвестна.

**Варианты для решения владельцем, ни один не выбран и не исполнен:** (A) принять явное narrowed поведение текущего scanner slice без публикации in-memory fragments и согласовать полный task-sourced spec/ТЗ после проверки актуальной applied history; (B) если partial preservation обязательно, отдельно спроектировать durable independently completed/sanitized per-check checkpoints с atomic cancel snapshot, ownership/attempt/revoke/lease fencing, immutable evidence и restart/redaction tests — без raw/incomplete stdout; (C) явно разделить narrowed slice и будущий full partial-cancel scope, оставив исходный критерий открытым. Это не review-only cosmetic fix; `declare_no_spec_impact` не может заменять согласование поведения. Здесь не меняются ни код, ни ТЗ/spec, ни tracker status. ## Ручной screen-reader gate: точный 5-minute checklist

### Почему не объявлен автоматический VoiceOver PASS

В доступных tools нет специализированного bounded API, который гарантированно управляет только этим browser context и возвращает достоверную озвученную VoiceOver/NVDA речь. CDP AX tree и MutationObserver доказывают доступный текст/семантику, **не факт произнесения, порядок или отсутствие дублей**. `osascript`/System Events, системное включение VoiceOver и запись общего audio/desktop затрагивают глобальные Accessibility permissions и могут прочитать другие окна; это не безопасный read-only обход. Такие действия не выполнялись. NVDA на macOS также не является доступным native инструментом этого прохода.

### Безопасный fixture стенд для оператора

Из `diplom`, в обычном операторском терминале:

```sh
node tests-e2e/final-accessibility.mjs --manual
```

Сначала выполняются те же automated checks; затем открытая isolated Chromium с synthetic API остаётся **не более 300 секунд**, полный deadline375s. Скрипт печатает реальные origin и три URL, так что не нужно угадывать порт или открывать существующий стенд. Ctrl+C во время operator hold закрывает browser/listener и удаляет temp cache. Не используйте настоящий account/profile/backend; не включайте scanner. Headed/manual mode здесь **не запускался** и audible результат не записывался. Если операторский Chromium/VoiceOver setup отличается, это нужно указать в протоколе.
